## 三个代理版本的演化（都是真 LLM，协议相同）

| 版本 | 机制 | K=50 表现 | 全档 PASS |
|---|---|---|---|
| v6 线程 | GIL 单核 + 429 即死 | 4/9 @ 1015s(多数派) | 33/45 |
| v7 fork | 无 GIL，无 429 处理 | 0/10（429 风暴团灭） | — |
| **v8 fork+cap** | **每连接 fork + 429 指数退避 + max_children=8 并发上限** | **10/10 @ 890s** | **38/40** |

## 关键发现

1. **z.ai 按 key 并发限流（HTTP 429 code 1302）是真实的第一瓶颈**：
   单发请求 200，10 沙盒×50 worker 齐射必触发；v6 时代"REQS=3 启动抖动"
   的沙盒其实也是 429。解法 = mini_proxy v8 的退避重试 + 并发上限。
2. **沙盒算力不是约束**：实测单沙盒可弹性用到 ~128 物理核（烧 CPU 108 核）、
   内存 32GB；两个沙盒同节点各 ~82 核。cpu.max 显示的 8 核未被执行。
3. **网关限制**：exec HTTP 连接 2 小时上限（504）；>2h 任务须 nohup 分离 +
   轮询收集。exec 按沙盒串行排队。
4. **幂等 worker 指令是协议层关键**：无它时单店重复发 25 次 ECHO、
   chief 永不收口；加上"只睡一次只发一次"后收口干净（ECHODIST 满额）。
5. **扩展形状与 mock 同构但系数不同**：mock（协议回放）191×@250agent；
   真 LLM 26×@50agent 峰值——差值全部来自 LLM 推理（~10-40s/次）、
   codex 进程启动、SSE 转换和限流退避。

## 与 mock 版对照

mock 最优 191×@250agent（纯协议扩展性）；真 LLM 版 26×@50agent（端到端真实性能）。
两者的差距就是"协调框架开销"与"每回合真实智能开销"的量化分解。
